# gsd-incident — 故障应急

> 线上故障不可避免，但"故障响应混乱"可以避免。本 skill 定义故障定级、应急流程、复盘模板，让团队在压力下也能有序行动。核心目标：**先恢复服务，再排查根因**。

## 何时使用

- 线上告警触发，需要判断严重程度
- 发生故障，需要按流程响应
- 故障恢复后，需要复盘
- 想提前准备应急 SOP

## 故障定级

收到告警后，**1 分钟内**完成定级。定级决定响应速度和资源投入。

| 等级 | 定义 | 响应时间 | 沟通范围 | 示例 |
|------|------|---------|---------|------|
| **P0** | 核心功能完全不可用，大面积用户受影响 | 立即，7×24 | 全员 + 管理层 + 客服 | 支付全挂、登录全挂、数据库宕机 |
| **P1** | 核心功能部分受损，或非核心功能全挂 | 15 分钟内 | 值班 + Tech Lead + 客服 | 下单偶发失败、某地区访问异常 |
| **P2** | 非核心功能受损，影响有限 | 1 小时内 | 值班 + 相关模块负责人 | 后台报表慢、通知延迟 |
| **P3** | 轻微问题，无明显用户影响 | 当天处理 | 值班 | 个别用户偶发报错、日志噪音 |

**定级原则**：拿不准往高定。P3 误判为 P1 最多浪费人力，P1 误判为 P3 会错过处置窗口。

## 应急响应流程（分四阶段）

### 阶段一：发现与定级（0-5 分钟）

```
告警触发 / 用户反馈
    │
    ├─ 值班人员确认告警真实性（排除误报）
    ├─ 1 分钟内定级（P0-P3）
    ├─ 拉群（P0/P1 立即拉，群名：[故障] 简述 + 时间）
    ├─ 通知相关方（客服准备话术、管理层知情）
    └─ 指定事故指挥官（Incident Commander，负责协调，不亲自排查）
```

**事故指挥官的职责**：
- 协调排查，不亲自 debug（让别人做）
- 记录时间线（什么时间做了什么）
- 决策（回滚？重启？扩容？）
- 对外沟通（进度同步）

### 阶段二：缓解与恢复（5-? 分钟）

**首要目标：恢复服务，不是找根因。**

按优先级尝试缓解手段：

| 手段 | 见效速度 | 风险 | 何时用 |
|------|---------|------|-------|
| 回滚 | 快（分钟级） | 低 | 刚部署完出问题 |
| 重启服务 | 快 | 低 | 内存泄漏、僵死 |
| 扩容 | 中（分钟级） | 低 | 流量暴涨 |
| 降级/限流 | 快 | 中 | 下游依赖挂 |
| 切流量到备库 | 中 | 中 | 主库故障 |
| 人工兜底 | 慢 | 高 | 自动化全失效 |

**决策树**：
```
刚部署完吗？
  ├─ 是 → 立即回滚（见 gsd-deploy 回滚决策树）
  └─ 否 →
       ├─ 能重启/扩容缓解吗？→ 做了再排查
       └─ 不能 →
            ├─ 是下游依赖问题？→ 降级/限流
            └─ 是自己问题？→ 定位 + 临时修复
```

**缓解动作必须记录**：什么时间、做了什么、效果如何。

### 阶段三：根因排查（恢复后）

服务恢复后，转入根因排查。**不要在服务未恢复时深挖根因**——用户在等。

排查方法：
1. 看时间线：故障开始时间 vs 最近变更
2. 看监控：哪个指标先异常
3. 看日志：异常时间点的 ERROR
4. 看链路：哪个环节慢/挂（见 gsd-observability）
5. 二分法：回滚到上一个稳定版本，逐步加变更定位

### 阶段四：复盘（48 小时内）

故障恢复后 **48 小时内**召开复盘会，产出复盘文档（见下方模板）。

**复盘铁律：对事不对人。** 找系统漏洞，不追个人责任。人都会犯错，系统应能承受单点失误。

## 复盘文档模板

```markdown
# 故障复盘：<简述> @ <日期>

## 概述
- 故障时间：2026-07-01 14:00 ~ 14:30（30 分钟）
- 影响范围：约 1200 笔支付失败
- 故障等级：P1
- 恢复方式：回滚到 v1.1.0

## 时间线
| 时间 | 事件 |
|------|------|
| 14:00 | 监控告警，支付失败率飙升 |
| 14:02 | 值班确认，定级 P1，拉群 |
| 14:05 | 确认是 v1.2.0 部署引起 |
| 14:10 | 决定回滚 |
| 14:15 | 回滚完成，服务恢复 |
| 14:30 | 全量恢复，观察 |

## 根因
<技术层面的根本原因，不只是表面现象>

v1.2.0 的退款逻辑在并发场景下触发了 DB 死锁。死锁原因是新加的索引与原有查询冲突，且事务内调用了外部 API（持有锁等响应）。

## 暴露的问题
1. 代码层面：事务内调用外部 API（违反工程规范）
2. 测试层面：并发场景未覆盖（测试缺失）
3. 部署层面：灰度比例直接 100%，未先小流量验证
4. 监控层面：DB 死锁告警延迟（应有实时死锁检测）
5. 流程层面：CR 未识别事务内外部调用问题

## 改进措施
| 措施 | 类型 | 负责人 | 截止 | 状态 |
|------|------|-------|------|------|
| 移除事务内外部调用 | 代码 | 张三 | 07-05 | 进行中 |
| 补充并发测试用例 | 测试 | 李四 | 07-08 | 待开始 |
| 灰度发布改为先 10% | 流程 | 王五 | 07-03 | 已完成 |
| 加 DB 死锁实时告警 | 监控 | 赵六 | 07-10 | 待开始 |
| CR 清单加"事务内外部调用"检查项 | 流程 | 钱七 | 07-05 | 已完成 |

## 经验教训
- 事务内绝不调外部 API（写入团队代码规范）
- 灰度发布必须从小比例开始
- 并发测试是发布前必过项
- DB 死锁应有独立监控，不能只靠应用层告警

## 附录
- 故障期间监控截图
- 相关 PR / Commit 链接
- 用户投诉记录
```

## 应急 SOP（按故障类型）

预先准备常见故障的处置手册，故障时照着做：

### 数据库宕机

```
1. 确认主库状态（连得上吗？进程在吗？）
2. 确认是否自动切换到备库（如已有主从）
3. 若未切换，评估手动切换 vs 等主库恢复
4. 切换后更新连接配置 / 刷新 DNS
5. 通知相关方，监控恢复
```

### 流量暴涨（被 DDoS 或营销爆量）

```
1. 确认流量来源（正常营销 vs 异常攻击）
2. 正常营销 → 紧急扩容
3. 异常攻击 → 接入 WAF / 限流 / 封 IP
4. 降级非核心功能（保支付登录）
5. 监控资源，避免雪崩
```

### 依赖服务挂

```
1. 确认哪个依赖挂（看 gsd-healthcheck 的 checks）
2. 启动降级方案（缓存兜底 / 默认值 / 排队）
3. 通知依赖方加急恢复
4. 持续监控依赖恢复，及时切回
```

### 数据误删 / 数据损坏

```
1. 立即停止相关写入（避免污染扩散）
2. 评估影响范围
3. 从备份恢复（见 gsd-migration 的备份要求）
4. 恢复后验证数据完整性
5. 排查误删原因（权限？bug？误操作？）
```

## 告警收敛（减少噪音）

告警太多会导致"告警疲劳"，真故障被淹没。定期治理：

| 治理动作 | 频率 |
|---------|------|
| 清理长期误报的告警规则 | 每月 |
| 合并重复告警（同一根因多个告警） | 每月 |
| 调整阈值（基于历史数据） | 每季度 |
| 下线已解决问题的临时告警 | 故障复盘后 |

**告警黄金法则**：每条告警都应有人响应。如果一条告警没人看，要么删掉，要么升级到有人看的级别。

## 与 gsd 工作流的衔接

- `gsd-deploy` 部署后异常 → 触发本 skill
- `gsd-healthcheck` 持续不健康 → 触发本 skill
- 本 skill 复盘的改进措施 → 录入团队待办，纳入 `/gsd-capture`
- 改进措施涉及代码 → 走 `/gsd-plan-phase` 规划修复
