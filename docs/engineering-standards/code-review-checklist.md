# Code Review 标准手册

> Code Review（CR）不是挑刺大会，而是团队最高效的技术交流方式。好的 CR 让代码质量提升、让知识流动、让团队对"好代码"达成共识。本手册定义 CR 的流程、标准与沟通规范。

---

## 一、CR 的价值与心态

### 1.1 为什么必须做 CR

| 价值 | 说明 |
|------|------|
| **质量兜底** | 工具查不出业务逻辑错误、架构不合理，只有人能判断 |
| **知识流动** | 审查者学习新写法，提交者获得改进，双向提升 |
| **集体所有权** | 代码不再"是你的"，而是"我们的"，人员流动不致灾难 |
| **早期发现问题** | 一个 CR 发现的问题，成本是线上事故的 1/100 |

### 1.2 正确心态

- **审查者**：你是合作者，不是裁判。目标是让代码更好，不是证明自己更强
- **提交者**：CR 反馈不是对你个人的否定，是让代码更稳。不要防御性回应
- **双方**：对事不对人。讨论"这段代码"，不讨论"你"

> 一条铁律：**任何代码合入主干前，至少经过一人 Review。** 没有例外，包括 Tech Lead 的代码。

## 二、CR 流程

### 2.1 标准流程

```
开发完成 → 自检 → 提交 PR/MR → 分配审查者 → 审查 → 反馈 → 修改 → 批准 → 合并
                                                              ↑
                                                          (可能多轮)
```

### 2.2 提交者职责

1. **先自检**：提交前对照"提交者自检清单"过一遍，别让低级问题浪费审查者时间
2. **写好 PR 描述**：说明做了什么、为什么这么做、如何测试的。PR 描述模板见附录
3. **控制 PR 规模**：单 PR 控制在 **400 行变更以内**。大功能拆成多个小 PR，每个可独立理解
4. **及时响应**：审查者的反馈 24 小时内响应（回应或修改），不让 PR 悬挂
5. **解释而非争论**：对反馈有异议时，解释你的考量，而非直接顶回去；仍达不成共识，拉第三方

### 2.3 审查者职责

1. **24 小时内开始审查**：不要让 PR 等你，开发节奏被打断影响全员
2. **先理解再评判**：先读懂 PR 的意图和上下文，再提意见。避免基于误解的批评
3. **反馈要可操作**：说"这里建议提取成方法，因为 XXX"而非"这里不好"
4. **区分严重等级**：用标签标注问题严重程度（见 2.5），让提交者知道哪些必须改
5. **肯定好设计**：看到优雅的写法、清晰的设计，明确赞扬，强化正向行为

### 2.4 审查者分配

- **小型 PR**：1 名审查者即可
- **中型 PR / 核心模块**：2 名审查者，其中 1 名为模块负责人或 Tech Lead
- **架构变更 / 跨模块影响**：2 名以上，需 Tech Lead 批准
- **避免单一审查者瓶颈**：轮换审查者，避免所有 PR 都堆给同一个人

### 2.5 反馈严重等级

每条反馈标注等级，提交者据此判断优先级：

| 标签 | 含义 | 提交者行动 |
|------|------|-----------|
| `[BLOCK]` | 必须修改，否则不合入。如：Bug、安全漏洞、架构问题、破坏契约 | 必须改 |
| `[SHOULD]` | 强烈建议修改。如：可读性差、违反规范、缺少测试 | 原则上改，确有理由可说明 |
| `[NIT]` | 吹毛求疵的小问题。如：变量名、空行、注释错别字 | 可改可不改，作者决定 |
| `[QUESTION]` | 不确定是否有问题，想了解意图 | 必须回应，澄清或确认 |
| `[PRAISE]` | 好设计/好写法，值得学习 | 作者开心，继续保持 |

```markdown
# 审查反馈示例

[BLOCK] 第 42 行：这里直接拼接 SQL，有注入风险，必须用参数化查询。
[SHOULD] `processData` 函数有 60 行，建议拆分成 validate + transform 两步。
[NIT] 变量 `d` 建议改成 `duration`，更易读。
[QUESTION] 这里用 sleep(100) 是为了等异步任务完成吗？有没有回调机制可用？
[PRAISE] 用策略模式替代 if-else 这块重构得很漂亮，以后其他人都能照着学。
```

## 三、CR 检查清单

### 3.1 提交者自检清单（提交前过一遍）

**功能与设计**
- [ ] 代码是否实现了 PR 描述中声明的功能？
- [ ] 是否处理了边界情况（空值、零、超长、并发）？
- [ ] 是否有更简单的实现方式？

**代码质量**
- [ ] 对照《代码规范通用指南》自检清单过一遍
- [ ] 命名是否准确、一致？
- [ ] 是否有死代码、注释掉的代码？
- [ ] 函数是否过长、嵌套是否过深？

**架构**
- [ ] 业务逻辑是否在正确的层？
- [ ] 是否引入了不必要的耦合？
- [ ] 新增功能是"加代码"还是"改一堆代码"？

**测试**
- [ ] 新增逻辑是否有对应测试？
- [ ] 边界情况是否被测试覆盖？
- [ ] 测试是否可独立运行（不依赖外部状态）？

**安全**
- [ ] 外部输入是否校验？
- [ ] 是否有 SQL 注入 / XSS 风险？
- [ ] 是否泄露敏感信息（日志、响应）？

**提交规范**
- [ ] Commit message 是否符合规范？
- [ ] PR 是否只包含相关变更（无无关文件混入）？
- [ ] PR 规模是否合理（<400 行）？

### 3.2 审查者检查清单

按优先级从高到低检查。**前四项是 BLOCK 级，发现问题必须打回。**

**1. 正确性（最高优先级）**
- [ ] 代码逻辑是否真的正确？手动跑一遍关键路径
- [ ] 边界条件是否处理（空、null、零、负数、超长、并发）？
- [ ] 错误处理是否完整（异常是否被吞、是否有兜底）？

**2. 安全性**
- [ ] 是否有注入风险（SQL、命令、XSS）？
- [ ] 权限校验是否到位（每个敏感操作都校验了？）？
- [ ] 敏感信息是否泄露（日志、错误响应、URL 参数）？
- [ ] 依赖是否有已知漏洞？

**3. 架构与设计**
- [ ] 业务逻辑是否在正确的层（不在 Controller、不在 Repository）？
- [ ] 是否引入了循环依赖或跨层穿透？
- [ ] 是否遵循 SOLID 原则（重点看 SRP 和 DIP）？
- [ ] 是否有过度设计或 YAGNI 违反？
- [ ] 新增功能是否是"加代码"而非"改一堆代码"？

**4. 性能**
- [ ] 是否有 N+1 查询？
- [ ] 循环内是否有 IO / DB 调用？
- [ ] 是否一次性加载大结果集（应分页）？
- [ ] 是否有内存泄漏风险（未释放的资源、无限增长的缓存）？

**5. 可读性**
- [ ] 命名是否准确？
- [ ] 是否需要注释来解释"为什么"？
- [ ] 嵌套是否过深（应改卫语句）？
- [ ] 函数是否过长？

**6. 可维护性**
- [ ] 是否有重复代码（三次法则）？
- [ ] 魔法值是否提取？
- [ ] 公开接口是否有文档注释？
- [ ] 是否留下无负责人无日期的 TODO？

**7. 测试**
- [ ] 新增逻辑是否有测试？
- [ ] 测试是否覆盖了边界和异常路径？
- [ ] 测试是否可独立运行、可重复？
- [ ] 测试命名是否说明了"测什么场景"？

**8. 规范一致性**
- [ ] 是否符合代码规范（格式由工具保证，重点看命名和结构）？
- [ ] 是否符合 Git 工作流规范（分支名、commit message）？

## 四、CR 沟通话术

### 4.1 反馈的表达原则

- **对代码不对人**：说"这段代码可以..."而非"你这里..."
- **用"建议"而非"命令"**：除非是 BLOCK 级
- **解释原因**：说"建议拆分，因为这个函数承担了校验和计算两个职责"而非"拆一下"
- **提具体方案**：给可操作的建议，而非只说"不好"
- **承认不确定**：不确定就用 QUESTION，不要假装权威

### 4.2 话术对照

| 场景 | ❌ 防御性 / 攻击性 | ✅ 建设性 |
|------|------------------|----------|
| 指出问题 | "这写错了" | "[BLOCK] 这里当 `list` 为空时会抛异常，建议加空判断" |
| 建议改进 | "这样太丑了" | "[SHOULD] 建议提取成 `validateInput` 方法，调用处更清晰" |
| 提问 | "你为什么不这样写？" | "[QUESTION] 这里用同步调用，是出于什么考虑？是否有异步方案？" |
| 不同意 | "不行" | "我理解你的思路，但担心 XXX，能否考虑 YYY 方案？" |
| 接受反馈 | （默默改） | "好的，已按建议修改，见最新 commit" |
| 解释保留 | "我就要这样" | "我保留这个写法，原因是 XXX；如果你觉得风险大，我可以加注释说明" |

### 4.3 处理分歧

1. **先理解对方**：复述对方的观点，确认理解无误
2. **基于事实**：用代码、文档、数据说话，而非"我觉得"
3. **找共识**：双方的目标都是代码更好，从共同点出发
4. **升级机制**：仍达不成共识，拉第三方（Tech Lead）仲裁，仲裁结果双方遵守
5. **不要在 PR 里长篇争论**：超过 5 轮未解决，转线下/语音讨论

## 五、不同类型代码的审查重点

### 5.1 新功能

重点：架构是否合理、是否可扩展、测试是否充分。容忍一定的迭代痕迹，但核心设计要对。

### 5.2 Bug 修复

重点：
- 是否找到了**根因**，还是只治了症状？
- 修复是否引入新问题？
- 是否补了**回归测试**（防止 bug 复现）？
- 是否有类似的其他地方存在同样 bug？

### 5.3 重构

重点：
- 行为是否保持不变（有测试保护）？
- 重构动机是否合理（不是为了重构而重构）？
- 是否分小步进行（大爆炸式重构风险极高）？
- PR 是否只含重构，无功能变更混入？

### 5.4 配置 / 基础设施变更

重点：
- 是否影响生产环境安全？
- 是否有回滚方案？
- 是否需要灰度？
- 密钥是否泄露？

### 5.5 依赖升级

重点：
- 是否有 Breaking Change？
- 升级动机（安全漏洞？新功能需要？）
- 是否全量测试通过？

## 六、CR 效率与反模式

### 6.1 提升 CR 效率

- **PR 要小**：400 行内的 PR 审查质量远高于 2000 行的。大功能拆 PR
- **PR 描述要全**：省了描述，审查者就要花时间猜，得不偿失
- **批量提反馈**：一次性把所有意见提完，别挤牙膏式一条条提
- **别囤 PR**：及时审、及时改，悬挂的 PR 是团队的最大阻塞

### 6.2 CR 反模式

- **橡皮图章**：看都不看直接 Approved。CR 流于形式，比不做更糟
- **吹毛求疵综合症**：全是 NIT 级意见，淹没真正重要的 BLOCK。审查者要分清主次
- **自行车棚效应**：在无关紧要的细节（变量名、空行）上争论半天，却忽视架构问题
- **PUA 式审查**：用贬低、嘲讽的语气提意见，破坏心理安全。一次就足以让人不敢提交
- **囤积式审查**：攒一堆 PR 才一次性看，审查质量下降且阻塞开发
- **只在 PR 阶段审查**：架构问题在 PR 阶段才发现为时已晚。复杂功能应先做设计评审

## 七、CR 度量

定期（每月）统计以下指标，评估 CR 健康度：

| 指标 | 健康范围 | 预警 |
|------|---------|------|
| PR 平均合入时长 | < 24 小时 | > 48 小时说明审查者不足或 PR 过大 |
| PR 平均变更行数 | < 400 行 | > 800 行说明未拆分 |
| 每个 PR 平均评论数 | 3-10 条 | < 1 条疑似橡皮图章；> 20 条疑似设计有问题 |
| BLOCK 级问题占比 | 10-30% | 过低说明审查不严，过高说明提交者自检缺失 |
| CR 参与度 | 全员参与 | 集中在 1-2 人说明有瓶颈 |

## 附录：PR 描述模板

```markdown
## 变更说明
<!-- 一句话说清做了什么 -->

## 变更类型
- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 配置/基础设施
- [ ] 依赖升级
- [ ] 文档

## 背景 / 动机
<!-- 为什么做这个变更？关联的 Issue/需求 -->

## 实现要点
<!-- 关键设计决策，帮审查者快速理解 -->

## 测试
- [ ] 单元测试已补充/更新
- [ ] 本地手动测试通过
- [ ] 边界情况已覆盖

## 影响范围
<!-- 影响哪些模块/功能？是否需要灰度？是否需要数据库迁移？ -->

## 风险与回滚
<!-- 已知风险？如何回滚？ -->

## 截图 / 日志（如适用）
<!-- UI 变更附截图，复杂逻辑附日志 -->

## 审查者关注点
<!-- 希望审查者重点看哪里？例如："重点看支付回调的幂等处理" -->
```
