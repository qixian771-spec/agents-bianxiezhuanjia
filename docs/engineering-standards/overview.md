# 团队工程化标准总纲

> 本文档是团队所有工程规范的"宪法"。其他规范文档（代码规范、架构原则、CR 手册、测试指南等）均以本文档为根，不得与之冲突。

---

## 一、为什么我们需要工程化标准

代码不只是写给机器执行的，更是**写给三个月后的自己和队友读的**。一个没有工程化标准的团队，迟早会陷入这样的困境：

- **规范不统一** → 每个人一套风格，代码像"多人合作作品"，阅读成本高
- **架构能力弱** → 耦合堆积，改一处动全身，越迭代越慢
- **质量无保障** → 测试缺失、CR 流于形式，线上问题反复
- **传承断层** → 关键知识锁在个别人脑子里，人员流动即灾难

工程化标准的本质，是**把个人经验沉淀为团队共识，把隐性知识转化为显性规则**。它不是束缚创造力的枷锁，而是让团队协作更顺畅、让每个人都能专注做有价值事情的基石。

## 二、核心工程理念

我们的工程实践遵循以下六条理念，优先级从高到低。当两条理念冲突时，**高优先级者胜出**。

### 1. 可读性 > 巧妙性

代码被阅读的次数远多于被编写的次数。"聪明"的代码（一行搞定、过度利用语言特性）往往是维护噩梦。优先选择**清晰直白**的写法，把"巧妙"留给真正需要性能优化的热点路径。

```python
# ❌ 巧妙但难懂
result = {k: v for k, v in map(lambda x: (x.id, x), filter(lambda x: x.active, items))}

# ✅ 清晰直白
result = {}
for item in items:
    if item.is_active:
        result[item.id] = item
```

### 2. 简单 > 灵活

"未来可能需要"是过度设计最常见的借口。YAGNI（You Aren't Gonna Need It）原则：**只为当前确定的需求设计**，但保留扩展的可能性。一个被实际使用的简单方案，胜过一个从未启用的灵活框架。

### 3. 显式 > 隐式

魔法（magic）是协作的敌人。状态变更、副作用、依赖注入、配置加载，都应当**可见、可追溯、可调试**。"约定优于配置"是好的，但"约定"必须被文档化，不能藏在某个人的脑子里。

### 4. 可测试 > 可运行

不能被测试的代码，就无法被安全地修改。每一段业务逻辑都应当是**可独立测试的单元**。这不是为了测试而测试，而是倒逼出更好的设计——难以测试的代码，往往设计也有问题。

### 5. 一致性 > 个人偏好

在团队协作中，**一致的中等方案好过分散的优秀方案**。统一了，才能自动化、才能复用、才能让新人快速上手。个人偏好让位于团队约定，但约定本身应当经过讨论、有理有据。

### 6. 性能优化基于度量

"我觉得这里慢"不构成优化的理由。性能优化必须**先有度量、定位瓶颈、再针对性优化**，并保留优化前后的基准数据。过早优化是万恶之源（Knuth），但该优化的热点路径要优化到位。

## 三、标准体系分层

整套工程化标准分为五个层级，从下往上依次构建。每一层都是上一层的基础，跳层建设会导致根基不稳。

```
┌─────────────────────────────────────────────┐
│  第五层：技术传承体系                          │  ← 团队成长路径
│  知识沉淀、新人 Onboarding、技术分享           │
├─────────────────────────────────────────────┤
│  第四层：质量保障体系                          │  ← CR 手册、测试指南
│  Code Review、自动化测试、CI/CD               │
├─────────────────────────────────────────────┤
│  第三层：架构设计体系                          │  ← 架构原则
│  设计模式、模块划分、依赖管理                   │
├─────────────────────────────────────────────┤
│  第二层：协作规范体系                          │  ← Git 工作流
│  分支模型、提交规范、PR 流程                    │
├─────────────────────────────────────────────┤
│  第一层：编码规范体系                          │  ← 代码规范指南
│  命名、格式、结构、错误处理                     │
└─────────────────────────────────────────────┘
```

| 层级 | 对应文档 | 核心目标 | 适用对象 |
|------|---------|---------|---------|
| 第一层 | `code-style-guide.md` | 让代码"长得一样" | 全员，每天 |
| 第二层 | `git-workflow.md` | 让协作不冲突 | 全员，每次提交 |
| 第三层 | `architecture-principles.md` | 让系统可演进 | Tech Lead、骨干 |
| 第四层 | `code-review-checklist.md` / `testing-standards.md` | 让质量可量化 | 全员，每个 PR |
| 第五层 | `team-growth-path.md` | 让能力可持续 | 全员，长期 |

## 四、技术栈适配原则

本团队是多技术栈混合团队。为避免"一套规范强行套所有语言"的水土不服，我们采用**"通用原则 + 技术栈专规"**的双层结构：

- **通用原则**：跨语言都成立的编码理念、架构思想、质量要求（见各总论文档）
- **技术栈专规**：针对具体语言/框架的细则（命名约定、目录结构、框架特性用法）

判断一条规则该放哪层，问自己：**"换一种语言，这条还成立吗？"** 成立→通用层；不成立→专规层。

### 已覆盖技术栈

当前专规覆盖以下技术栈，新增技术栈时需补充对应专规：

- PHP / Laravel / Livewire（详见 `tech-stack/laravel-livewire.md`）
- JavaScript / TypeScript / Vue / React（详见 `tech-stack/frontend.md`）
- Python（详见 `tech-stack/python.md`）
- Node.js（详见 `tech-stack/nodejs.md`）

> 其他语言（Java、Go 等）暂以通用规范为准，待团队使用规模扩大后补充专规。

## 五、规范的执行机制

规范写了不执行，等于没写。我们通过以下机制确保规范落地：

### 1. 自动化优先

能用工具卡住的规则，**绝不靠人肉检查**。例如：

- 代码格式 → Prettier / EditorConfig / PHP CS Fixer / Black
- 代码规范 → ESLint / PHPStan / Ruff / SonarQube
- 提交信息 → commitlint + husky
- 类型检查 → TypeScript / PHPStan / mypy

工具卡不住的，才进入人工 Code Review 的检查清单。

### 2. Code Review 把关

所有代码合入主干前必须经过至少一人 Review。Review 不是挑刺，而是**双向学习**——审查者学习新写法，提交者获得改进建议。详见 `code-review-checklist.md`。

### 3. 规范的演进

规范不是刻在石头上的。任何成员都可以发起规范修订提议：

1. 在规范仓库提 Issue，说明修订理由和影响范围
2. 经 Tech Lead 评审，团队讨论
3. 通过后更新文档，标注修订日期和原因
4. 在下一次技术同步会上宣贯

**规范的权威性来自共识，而非权威本身。** 但一旦达成共识，就必须遵守，个人不得擅自偏离。

### 4. 新人 Onboarding

新成员入职第一周必须通读第一、二层规范并完成一个"规范练习 PR"；第二周通读第三、四层并在 Mentor 指导下参与 CR。详见 `team-growth-path.md`。

## 六、落地路线图

罗马不是一天建成的。规范的落地按以下节奏推进，避免一次性铺开导致团队消化不良：

| 阶段 | 周期 | 目标 | 关键动作 |
|------|------|------|---------|
| **阶段一：地基** | 第 1-2 周 | 统一编码与协作规范 | 落地第一、二层，配置 lint/format 工具，全员对齐 |
| **阶段二：质量** | 第 3-4 周 | 建立质量门禁 | 落地第四层，CR 流程跑通，核心模块补测试 |
| **阶段三：架构** | 第 5-8 周 | 架构能力提升 | 落地第三层，新功能按规范设计，存量逐步重构 |
| **阶段四：传承** | 持续 | 形成自驱成长 | 落地第五层，技术分享常态化，知识库建设 |

每个阶段结束做一次回顾，评估落地效果（可通过代码扫描、CR 统计、Bug 率等指标），再决定是否进入下一阶段。

## 八、一句话总结

> **工程化标准的目标不是写出"完美"的代码，而是让团队协作的成本最低、让质量的下限可控、让每一个成员都能持续成长。** 规范是手段，人和产品才是目的。
