# 团队技术成长路径

> 技术传承断层是团队最隐蔽的危机——平时看不见，关键人离职时才爆发。本指南建立能力模型、学习路径和知识沉淀机制，让团队的技术能力**可积累、可传承、可复制**，而非锁在个别人脑子里。

---

## 一、问题诊断

技术传承断层通常表现为：

- **新人上手慢**：没有文档、没人带，靠"读代码"摸几个月
- **知识单点依赖**：某个系统只有一个人懂，这人休假就停摆
- **经验不沉淀**：踩过的坑反复踩，解决方案每次重新发明
- **成长无方向**：不知道该学什么、怎么进阶，靠天赋和运气
- **Bus Factor = 1**：关键人员一旦离开，系统即陷入混乱

**Bus Factor**（巴士因子）：团队中有多少人被巴士撞倒后项目就停摆。健康的团队 Bus Factor ≥ 3。

本指南的目标：**把 Bus Factor 从 1 提升到 3 以上。**

## 二、技术能力模型

定义四级技术能力，每级有明确的能力要求和判定标准。用于：晋升评估、自我定位、制定学习计划。

### 2.1 L1 初级开发者（0-2 年）

**能力特征**：能在指导下完成明确任务。

| 维度 | 要求 |
|------|------|
| 编码 | 熟练使用至少一门语言，写出能运行的代码 |
| 规范 | 遵守团队代码规范，通过 lint 检查 |
| 测试 | 能为自己的代码写基本单元测试 |
| 协作 | 熟悉 Git 基本操作，能提交规范的 PR |
| 调试 | 能定位和修复简单的 Bug |
| 学习 | 主动学习新技术，能读懂官方文档 |

**晋升标准**：能独立完成一个中等复杂度功能（含测试），无需他人持续指导。

### 2.2 L2 中级开发者（2-4 年）

**能力特征**：能独立完成模块级开发。

| 维度 | 要求 |
|------|------|
| 编码 | 代码清晰、可维护，能处理复杂业务逻辑 |
| 架构 | 理解分层架构，能在 Service/Repository 等层正确放置逻辑 |
| 测试 | 主导测试设计，覆盖核心路径和边界 |
| 协作 | 能担任 Code Review 审查者，给出建设性反馈 |
| 调试 | 能排查跨模块、跨服务的复杂问题 |
| 设计 | 能完成模块级技术设计，编写设计文档 |
| 影响力 | 帮助新人，分享踩坑经验 |

**晋升标准**：能独立负责一个模块从设计到上线全流程，且至少带过 1 个新人。

### 2.3 L3 高级开发者 / Tech Lead（4-7 年）

**能力特征**：能主导系统设计和技术决策。

| 维度 | 要求 |
|------|------|
| 架构 | 主导系统架构设计，做关键技术选型和权衡 |
| 设计 | 能做跨模块、跨系统的技术方案设计 |
| 质量 | 建立质量标准，把关关键 PR，识别架构风险 |
| 技术债 | 识别技术债，制定偿还计划，平衡业务与技术 |
| 难题 | 攻克技术难题（性能、并发、一致性等） |
| 影响力 | 技术分享、 mentor 中级开发者、跨团队协作 |
| 文档 | 主导架构文档、ADR、技术规范编写 |

**晋升标准**：主导过至少一个核心系统的架构设计并成功落地，培养出至少 1 名 L2。

### 2.4 L4 资深 / 架构师（7 年+）

**能力特征**：技术视野覆盖全栈，能做组织级技术决策。

| 维度 | 要求 |
|------|------|
| 架构 | 主导多个系统的整体架构，做组织级技术战略 |
| 技术视野 | 跟踪前沿技术，判断适用性和引入时机 |
| 技术债 | 在业务发展中系统性管理技术债，避免积重难返 |
| 影响力 | 建立团队技术文化，培养多名 Tech Lead |
| 业务理解 | 深度理解业务，用技术驱动业务创新 |
| 决策 | 在不确定性下做技术决策并承担责任 |

## 三、成长路径与学习指南

### 3.1 通用成长建议

**1. 扎实基础，而非追逐框架**

框架会过时，基础长青。优先投入：
- 数据结构与算法（决定你代码的效率思维）
- 操作系统、网络、数据库原理（决定你排查问题的深度）
- 设计模式与原则（决定你代码的质量上限）
- 至少一门语言的深入（而非三门语言的皮毛）

**2. 读优质代码**

成长最快的方式之一：读优秀的开源项目代码。看高手怎么组织代码、怎么命名、怎么处理边界。推荐从你用的框架源码读起。

**3. 写技术总结**

学完一个东西，用自己的话写出来。写不出来的，说明没真懂。坚持写技术博客 / 内部 wiki，倒逼深度思考。

**4. 主动承担难题**

舒适区里长不出能力。主动认领有挑战的任务（性能优化、架构重构、新技术预研），在实战中成长。

**5. 复盘而非重复**

做完一个项目，问自己：哪里做得好？哪里可以更好？下次怎么改进？不复盘的经验只是经历，复盘过的才是能力。

### 3.2 各级别学习重点

**L1 → L2 重点**：
- 精通主力语言（读《代码整洁之道》《重构》）
- 掌握主力框架（读官方文档 + 源码）
- 数据库基础（SQL、索引、事务）
- Git 进阶（rebase、冲突解决）
- 测试方法（单元测试、Mock）
- 基本设计模式

**L2 → L3 重点**：
- 架构设计（《领域驱动设计》《架构整洁之道》）
- 系统设计（分布式、缓存、消息队列、一致性）
- 性能优化（ profiling、瓶颈分析）
- 技术写作（设计文档、ADR）
- Code Review 能力
- 跨团队沟通

**L3 → L4 重点**：
- 大规模系统架构（《数据密集型应用系统设计》）
- 技术战略与规划
- 技术团队管理
- 业务深度理解
- 技术选型与风险评估
- 影响力建设（分享、布道、社区）

### 3.3 推荐书单（分阶段）

**夯实基础**：
- 《代码整洁之道》— Robert Martin
- 《重构》— Martin Fowler
- 《代码大全》— Steve McConnell
- 《程序员的自我修养》— 俞甲子

**进阶架构**：
- 《架构整洁之道》— Robert Martin
- 《领域驱动设计》— Eric Evans
- 《数据密集型应用系统设计》— Martin Kleppmann
- 《微服务架构设计模式》— Chris Richardson

**工程实践**：
- 《持续交付》— Jez Humble
- 《Site Reliability Engineering》— Google
- 《凤凰架构》— 周志明

## 四、知识沉淀机制

### 4.1 三层知识库

```
┌─────────────────────────────────┐
│  团队 Wiki（长期知识）            │  架构、规范、最佳实践、技术决策
├─────────────────────────────────┤
│  代码内文档（即时知识）           │  README、ADR、注释、API 文档
├─────────────────────────────────┤
│  事后文档（经验知识）             │  复盘报告、踩坑记录、故障分析
└─────────────────────────────────┘
```

### 4.2 知识沉淀时机

**强制沉淀**（不沉淀视为未完成）：
- 重大技术决策 → 写 ADR
- 线上故障 → 写故障复盘
- 新系统/大功能上线 → 写架构文档
- 踩了非平凡的坑 → 写踩坑记录

**鼓励沉淀**：
- 有价值的调试经验
- 性能优化案例（含数据）
- 新技术调研结论

### 4.3 ADR（架构决策记录）

每个不可逆的技术决策都要有 ADR，记录**为什么选这个、为什么不选那个**。这是给未来的礼物——半年后没人记得为什么这么选，ADR 是唯一的真相。

ADR 模板见《架构设计原则与实践》第九章。

### 4.4 故障复盘

线上故障后 48 小时内召开复盘会，产出复盘文档：

```markdown
# 故障复盘：2026-07-01 支付服务不可用

## 故障概述
- 时间：2026-07-01 14:00 - 14:30（30 分钟）
- 影响：约 1200 笔支付失败
- 等级：P1

## 时间线
- 14:00  监控告警，支付失败率飙升
- 14:05  值班确认，启动应急
- 14:15  定位为 DB 连接池耗尽
- 14:25  扩容连接池，服务恢复
- 14:30  全量恢复，观察

## 根因
支付服务在高峰期连接池配置过小（50），且存在连接泄漏（异常路径未释放）。

## 暴露的问题
1. 连接池容量未按峰值评估
2. 异常路径资源释放缺失
3. 监控只告警失败率，未提前预警连接池使用率

## 改进措施
| 措施 | 负责人 | 截止日期 | 状态 |
|------|-------|---------|------|
| 修复连接泄漏 | 张三 | 07-05 | 进行中 |
| 连接池扩容至 200 | 李四 | 07-03 | 已完成 |
| 增加连接池使用率监控 | 王五 | 07-08 | 待开始 |
| 补充连接池压测 | 赵六 | 07-15 | 待开始 |

## 经验教训
- 资源类配置必须基于峰值压测，而非"够用就行"
- 异常路径的资源释放要用 try-finally 保证
- 监控要领先于故障，而非等失败率告警
```

**复盘原则**：对事不对人，找根因而非追责，每个问题都要有改进措施和负责人。

### 4.5 踩坑记录

踩过的坑是团队最宝贵的资产。维护一个"踩坑库"，按主题分类：

```markdown
# 踩坑记录：Laravel 队列任务幂等性

## 现象
队列任务被重复消费，导致用户被重复发邮件。

## 原因
Laravel 队列在 worker 崩溃时会重试任务，但任务本身未做幂等设计。

## 解决
任务开始前用 Redis SETNX 加锁，已处理过的任务直接跳过。

## 通用教训
所有队列任务、回调、重试接口必须幂等。设计时假设"这段代码会被执行多次"。
```

## 五、新人 Onboarding

### 5.1 Onboarding 目标

新人入职后：
- **第 1 周**：环境跑通，读规范，理解项目全貌
- **第 2 周**：完成第一个小功能（含测试、走完 PR 流程）
- **第 1 个月**：能独立完成中等功能
- **第 3 个月**：成为某个模块的熟悉者

### 5.2 Onboarding 清单

**入职第一天**：
- [ ] 分配 Mentor（师父）
- [ ] 开通各系统账号（代码库、Wiki、CI、监控）
- [ ] 本地开发环境搭建（有文档）
- [ ] 能跑通项目、跑通测试

**第一周**：
- [ ] 通读《工程化标准总纲》《代码规范》《Git 工作流》
- [ ] Mentor 讲解系统架构（有架构图）
- [ ] 读项目 README 和核心模块文档
- [ ] 完成一个"练习 PR"（修个小 bug 或加个小功能，走完整 PR 流程）

**第一个月**：
- [ ] 独立完成 2-3 个中等功能
- [ ] 参与 Code Review（先作为提交者，再作为审查者）
- [ ] Mentor 每周 1:1，解答疑问、反馈进展
- [ ] 旁听一次技术分享

### 5.3 Mentor 职责

Mentor 不是"布置任务的"，而是"帮助新人成长的"：

- **环境保障**：确保新人能快速跑通环境，别卡在配置上
- **任务引导**：分配合适难度的任务，由易到难
- **随时答疑**：新人问题优先响应，别让人憋着
- **代码指导**：新人的 PR 认真审，讲清楚"为什么这么改"
- **定期反馈**：每周 1:1，聊进展、聊困惑、聊成长
- **放权信任**：新人上手后逐步放手，别一直盯着

### 5.4 避免"扔进水里学游泳"

最常见的反模式：给新人一个任务，然后不管，美其名曰"锻炼独立能力"。这不叫培养，叫放弃。新人前期的挫败感会极大影响留存。**Mentor 的陪伴是 Onboarding 成败的关键。**

## 六、技术分享与学习文化

### 6.1 技术分享会

- **频率**：每两周一次，每次 30-45 分钟
- **形式**：一人主讲 + 讨论
- **主题**：新技术调研、踩坑总结、好书分享、架构设计
- **轮值**：全员轮值，避免总是一两个人讲
- **记录**：分享内容沉淀到 Wiki

### 6.2 读书会

- 选一本技术书，每周读一章，集体讨论
- 适合夯实基础的阶段（如团队一起读《代码整洁之道》）

### 6.3 结对编程

- 难题攻关、新人指导、复杂重构时用
- 两人一台电脑，一人敲一人看，15 分钟轮换
- 知识在结对中流动，比文档更生动

### 6.4 技术雷达

团队维护一份"技术雷达"：我们用什么、试什么、弃什么。让技术选型有共识，而非每人各玩各的。

```
采纳：Laravel、Vue3、PostgreSQL、Redis
试验：Rust、GraphQL
暂缓：微服务（团队规模未到）
弃用：jQuery、PHP 7.x
```

## 七、Code Review 作为培养手段

Code Review 不只是质量把关，更是**最高频的技术培养场景**：

- **审查者**：通过审查别人的代码，学习不同写法，锻炼"发现问题的眼力"
- **提交者**：从反馈中学习改进，理解"好代码"的标准
- **新人**：被审 PR 的反馈是最好的 1:1 教学

鼓励新人尽早参与 Review（哪怕只提 QUESTION），从"被审"逐步过渡到"审查别人"。

## 八、技术传承的保障措施

### 8.1 模块负责人制

每个核心模块指定 1 名**主负责人** + 1 名**备份负责人**：
- 主负责人：日常开发、技术决策、代码把关
- 备份负责人：参与 Review、了解设计、能独立维护

**关键点**：备份负责人必须实际参与过该模块的开发和 Review，不能只是"挂名"。每季度轮换一次，避免固化。

### 8.2 文档与代码同步

文档过时比没有文档更糟。规则：
- 架构变更必须同步更新架构文档（PR 检查清单包含此项）
- ADR 只增不改（历史决策是历史，新决策写新 ADR）
- README 的"快速启动"必须随时可用（新人入职验证）

### 8.3 定期知识转移

- 每季度举办"模块讲解会"：每个模块负责人给团队讲一遍自己的模块
- 关键系统的设计文档，团队共读讨论
- 避免知识只在"会议纪要"里，要落到 Wiki

### 8.4 代码注释与提交历史的价值

好的代码注释和 commit history 本身就是知识传承：
- 注释解释"为什么这么做"（决策理由）
- commit message 说明"改了什么、为什么改"

新人通过 `git log` 和注释就能理解大部分历史决策，不用揪着老人问。

## 九、健康度自检

每季度评估团队技术健康度：

| 维度 | 健康信号 | 预警信号 |
|------|---------|---------|
| Bus Factor | 关键模块 ≥ 2 人熟悉 | 只 1 人懂的模块 > 3 个 |
| 知识沉淀 | Wiki 活跃、ADR 齐全 | 关键系统无文档 |
| 新人成长 | 新人 1 个月内能产出 | 新人 3 个月仍迷茫 |
| 技术分享 | 定期举办、全员参与 | 流于形式或停办 |
| 代码质量 | CR 活跃、测试覆盖达标 | CR 橡皮图章、测试缺失 |
| 技术债 | 有清单、有计划 | 债务堆积、无人问津 |

---

## 十、一句话总结

> **团队的技术能力不是个人能力的简单相加，而是沉淀在文档、规范、代码和协作流程中的集体智慧。** 把个人经验变成团队资产，把"我记得"变成"文档里写着"，传承就不再依赖某个人。
