# 团队工程化标准体系

> 一套系统化、可落地的工程规范，帮助多技术栈团队统一代码质量、提升架构能力、建立质量保障、形成技术传承。
>
> 维护者：Senior Developer（高级开发工程师）｜ 版本：v1.0 ｜ 更新：2026-07-02

---

## 这套规范解决什么问题

针对团队的四大痛点设计：

| 痛点 | 对应文档 | 核心解法 |
|------|---------|---------|
| 代码规范不统一 | 代码规范通用指南 + Git 工作流 | 跨语言通用规范 + 工具自动化 + 分支/提交规范 |
| 架构设计能力弱 | 架构设计原则与实践 | SOLID 原则 + 分层架构 + 决策框架 + 反模式清单 |
| 代码质量/测试缺失 | Code Review 手册 + 测试指南 | CR 流程与清单 + 测试金字塔 + CI 集成 |
| 技术传承断层 | 团队技术成长路径 | 能力模型 + 知识沉淀 + Onboarding + 模块负责人制 |

## 文档结构

整套规范分五层，建议按顺序阅读、分层落地：

### 第一层：编码规范（全员，每天）
- **[代码规范通用指南](./code-style-guide.md)** — 跨语言通用的命名、格式、注释、错误处理、函数设计、安全基线，配多语言示例和自检清单

### 第二层：协作规范（全员，每次提交）
- **[Git 工作流规范](./git-workflow.md)** — 分支模型、Conventional Commits、PR 流程、合并策略、版本管理、敏感信息防护

### 第三层：架构设计（Tech Lead / 骨干）
- **[架构设计原则与实践](./architecture-principles.md)** — SOLID 原则、分层架构、模块化边界、常用模式、决策框架、反模式清单、ADR 模板

### 第四层：质量保障（全员，每个 PR）
- **[Code Review 标准手册](./code-review-checklist.md)** — CR 流程、严重等级标签、提交者/审查者检查清单、沟通话术、度量指标
- **[测试工程化指南](./testing-standards.md)** — 测试金字塔、FIRST 原则、各技术栈实践、覆盖率目标、CI 集成、反模式

### 第五层：技术传承（全员，长期）
- **[团队技术成长路径](./team-growth-path.md)** — 四级能力模型、学习路径、推荐书单、知识沉淀机制、新人 Onboarding、模块负责人制

### 总纲
- **[工程化标准总纲](./overview.md)** — 体系的"宪法"，核心理念、标准分层、落地路线图

## 如何使用

### 给团队 Leader / Tech Lead

1. **先读总纲**：理解整体框架和落地节奏
2. **按路线图推进**：不要一次铺开，分四周分阶段落地（见总纲第六章）
3. **工具优先**：能用 lint/format 工具卡住的规则，别靠人肉检查
4. **以身作则**：Leader 的代码也要走 CR，规范才能服众

### 给每位开发者

1. **入职第一周**：通读第一、二层，完成一个练习 PR
2. **入职第二周**：通读第四层，在 Mentor 指导下参与 CR
3. **日常开发**：每次提交前对照"自检清单"
4. **持续成长**：对照能力模型定位自己，按学习路径进阶

### 给新人

1. **第一天**：Mentor 帮你跑通环境
2. **第一周**：读规范 + 完成小功能 PR（走完整流程）
3. **不懂就问**：Mentor 和团队都在，别憋着
4. **三个月后**：成为某个模块的熟悉者

## 落地路线图（4 周计划）

| 周 | 阶段 | 目标 | 关键动作 |
|----|------|------|---------|
| 第 1-2 周 | 地基 | 统一编码与协作 | 落地第一、二层，配置 lint/format，全员对齐 |
| 第 3-4 周 | 质量 | 建立质量门禁 | 落地第四层，CR 流程跑通，核心模块补测试 |
| 第 5-8 周 | 架构 | 架构能力提升 | 落地第三层，新功能按规范设计，存量逐步重构 |
| 持续 | 传承 | 自驱成长 | 落地第五层，技术分享常态化，知识库建设 |

每个阶段结束做回顾，评估落地效果（代码扫描、CR 统计、Bug 率等指标）。

## 核心理念（一句话版）

> **工程化标准的目标不是写出"完美"的代码，而是让团队协作成本最低、让质量下限可控、让每个成员都能持续成长。规范是手段，人和产品才是目的。**

## 规范的演进

规范不是刻在石头上的。任何成员可发起修订：

1. 提 Issue 说明修订理由和影响范围
2. Tech Lead 评审，团队讨论
3. 通过后更新文档，标注修订日期
4. 下次技术同步会宣贯

**规范的权威性来自共识，但一旦达成共识就必须遵守。**
