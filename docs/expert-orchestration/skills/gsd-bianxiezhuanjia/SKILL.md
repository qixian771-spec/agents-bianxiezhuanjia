# /gsd-bianxiezhuanjia — 编写专家框架

> 编排"开发专家"把 MVP 调优成可用应用的统一入口。gsd 自带的 `/gsd-plan` `/gsd-impl` `/gsd-ship` 产出 MVP 后，用本命令进入专家编排阶段——对业务流水线里的"发散节点"（仿写、Remotion 合成等）施加专家约束，把"能跑通的 MVP"调优成"可重复产出的可用应用"，再交给 `/gsd-deploy` 部署。
>
> 本命令是**编排入口 + 专家调度器**，本身不写业务代码，只做：初始化流水线、扫描进度、提示下一步调谁、激活专家时做门禁、跑专家收敛逻辑。

## 何时使用

- `/gsd-ship` 完成 MVP 后，想把 MVP 调优成可用应用
- 流水线跑到一半，想看当前进度、确认下一步调谁
- 某个节点重跑后，想确认下游是否需要同步重跑
- 首次进入编排模式，需要初始化流水线配置

## 子命令路由

本命令用第一个参数路由到不同操作：

| 命令 | 作用 | 拼音记忆 |
|------|------|---------|
| `/gsd-bianxiezhuanjia init` | 初始化编排工作区 + pipeline.json | 因尼特 |
| `/gsd-bianxiezhuanjia` | 看流水线进度（默认行为） | — |
| `/gsd-bianxiezhuanjia status` | 同上，看进度 | 斯特特斯 |
| `/gsd-bianxiezhuanjia copywrite` | 跑仿写专家（收敛文案风格/结构/时长） | 考皮莱特 |
| `/gsd-bianxiezhuanjia remotion` | 跑 Remotion 专家（收敛合成代码结构） | 瑞莫申 |
| `/gsd-bianxiezhuanjia exit` | 退出编排模式 | 埃克西特 |

**只记一个命令** `/gsd-bianxiezhuanjia`，按 Tab 看子命令提示。无参数 = 看进度。

# 子命令：init — 初始化编排工作区

## 何时跑

- 首次进入编排模式，`.gsd-expert/` 不存在
- 想重置流水线（清空重来）

## 执行流程

### 第 1 步：确认工作区

检查项目根的 `.gsd-expert/` 是否存在：
- 不存在 → 创建目录结构
- 已存在 → 警告「检测到已有编排工作区，init 会清空现有 state 和 artifacts。是否继续？」需用户确认

目录结构（创建空骨架）：

```
.gsd-expert/
├── context/
├── state/
├── artifacts/
└── log/
```

### 第 2 步：引导填写 pipeline.json

询问用户（或从当前项目上下文推断）：

1. **流水线类型**：voiceover（口播）/ graphic（图文）/ clip（直播切片）/ custom
   - 选预设类型 → 加载对应模板（当前仅口播模板）
   - 选 custom → 逐个询问节点
2. **账号信息**：名称、人设、风格指南
3. **目标参数**：目标平台、目标时长等

### 第 3 步：生成 pipeline.json

按 [编排流程](../../orchestration-flow.md) 第二章的 schema 生成 `.gsd-expert/context/pipeline.json`：

```json
{
  "$schema": "pipeline-context/v1",
  "pipeline-id": "<auto-generated>",
  "pipeline-type": "<voiceover|graphic|clip|custom>",
  "created-at": "<now ISO>",
  "account": { "name": "...", "persona": "...", "style-guide": "..." },
  "nodes": [
    { "id": "node-1", "type": "tool", "name": "..." },
    { "id": "node-2", "type": "expert", "name": "...", "expert": "copywrite" }
  ]
}
```

`nodes` 里 `type: expert` 的节点必须带 `expert` 字段，编排器据此知道哪些节点走专家调度。

### 第 4 步：初始化完成提示

```
✓ 编排工作区已初始化：.gsd-expert/
✓ 流水线配置已生成：context/pipeline.json（voiceover，6 节点）

下一步：逐个跑节点。
  → tool 节点：直接调对应工具
  → expert 节点：/gsd-bianxiezhuanjia copywrite（仿写）/ remotion（合成）

输入 /gsd-bianxiezhuanjia 查看进度。
```

# 子命令：status（默认）— 看流水线进度

## 做什么

扫描 `.gsd-expert/state/` 下所有状态文件，结合 `context/pipeline.json` 重建当前 DAG 进度，提示哪些节点可激活、哪些被阻塞。

## 执行流程

### 第 1 步：读取流水线定义

读 `.gsd-expert/context/pipeline.json`：
- 不存在 → 提示「未初始化，请先 /gsd-bianxiezhuanjia init」
- 存在 → 取 `nodes` 列表

### 第 2 步：逐节点扫描状态

对 `nodes` 里的每个节点，读 `state/<node-id>.<expert-or-name>.json`：

| 状态文件情况 | 判定 |
|-------------|------|
| 文件存在 + `status: completed` | ✓ 已完成 |
| 文件存在 + `status: partial` | ⚠ 完成但质量门禁未过（需人决策） |
| 文件存在 + `status: failed` | ✗ 失败（需重跑或介入） |
| 文件不存在 | ○ 未开始 |

记录每个完成节点的 `completed-at` 时间戳，用于下游感知上游更新。

### 第 3 步：判断每个未完成节点的可激活性

对每个未完成（○ / ⚠ / ✗）的节点，检查其 `input-contract.required`：

- 节点是 **tool**（`type: tool`）：检查隐式上游是否 completed
- 节点是 **expert**（`type: expert`）：读对应专家的协议字段（见 `references/expert-*.md`），取 `input-contract.required`，检查每个 `source` 指向的状态文件是否存在且 `completed`

判定结果：

| 情况 | 标记 | 提示 |
|------|------|------|
| 所有 required 上游 completed | **可激活** | 「→ 可执行 /gsd-bianxiezhuanjia <子命令>」或「→ 可跑 tool <name>」 |
| 有上游未完成 | **阻塞** | 「← 阻塞：缺 <upstream-node>」 |
| 有上游 partial | **阻塞（质量未过）** | 「← 阻塞：<upstream> 质量门禁未过」 |
| 有上游 failed | **阻塞（上游失败）** | 「← 阻塞：<upstream> 失败」 |

### 第 4 步：检测"上游已更新，建议重跑下游"

对已 completed 的节点，检查其所有上游的 `completed-at`：
- 若任一上游的 `completed-at` 晚于本节点 → 标记为 **可能过期**，提示「↑ 上游已更新，建议重跑本节点」

这是人工接力模式下感知"重跑传播"的关键机制。

### 第 5 步：输出进度表

**呈现规则**（模拟验证发现，必须遵守）：

1. **每个节点在进度表里只出现一行**——状态、时间戳、质量门禁、阻塞原因都合并到这一行，不在表外单独列阻塞段
2. **"可激活"和"可能过期"在表后单独成段**
3. **"可能过期"独立于"全部完成"判断**——即使所有节点都 completed，只要有下游的 `completed-at` 早于上游，仍要显示

格式（进行中）：

```
口播流水线 voiceover-001
─────────────────────────────────────────────────────
  node-1 去水印抓文案      ✓ completed  15:05
  node-2 仿写文案(专家)    ✓ completed  15:31  质量门禁 4/4
  node-3 TTS              ✓ completed  15:40
  node-4 数字人            ○ 未开始
  node-5 Remotion(专家)    ○ 未开始  ← 阻塞：缺 node-4
  node-6 自动发布          ○ 未开始  ← 阻塞：缺 node-5
─────────────────────────────────────────────────────
可激活：
  → node-4 是 tool，直接调数字人服务
  → node-4 完成后，node-5 可执行 /gsd-bianxiezhuanjia remotion

可能过期：（无）
```

格式（全部完成）：

```
口播流水线 voiceover-001  ✓ 全部完成
  ...（各节点状态）
─────────────────────────────────────────────────────
可用应用就绪。
  → 可执行 /gsd-deploy 部署
  → 或 /gsd-bianxiezhuanjia exit 退出编排模式
```

格式（全部完成 + 有下游过期，重跑上游后常见）：

```
口播流水线 voiceover-001  ✓ 全部完成
  node-1 ...              ✓ completed  15:05
  node-2 仿写文案(专家)    ✓ completed  16:00  质量门禁 4/4   ← 刚重跑
  node-3 TTS              ✓ completed  15:40
  ...
─────────────────────────────────────────────────────
可用应用就绪。
  → 可执行 /gsd-deploy 部署
可能过期（上游已更新，建议重跑）：
  ↑ node-3 TTS：上游 state/node-2.copywrite.json 已更新
  ↑ node-5 Remotion：上游 state/node-2.copywrite.json 已更新
```

> 这种情况下，虽然"全部完成"，但部分下游基于旧上游产出——是否重跑由人决策，编排器只提示不强制。

# 子命令：copywrite — 仿写文案专家

## 做什么

对节点1 抽取的原文案做**风格一致**的仿写，输出带结构标记的文案，供下游 TTS、数字人、Remotion 消费。核心职责不是"写出文案"，而是"收敛仿写的发散性"——保证风格稳、结构全、时长准。

## 前置门禁（激活前必查）

```
state/node-1.extract.json 存在且 status=completed？
  → 否：拒绝，提示「仿写需要 node-1 完成，当前缺失」
  → 是：放行，进入仿写流程
```

## 详细流程

**完整的仿写流程、收敛约束、质量门禁检查清单、产出 schema 见 [`references/expert-copywrite.md`](./references/expert-copywrite.md)。**

执行本子命令时，按该文档的 5 步流程跑：
1. 读取输入（node-1 状态 + pipeline 上下文）
2. 解构原文案风格指纹
3. 仿写（带结构对齐/段标记/禁用词/时长四大约束）
4. 质量门禁（6 项检查全过才 completed，否则 partial）
5. 产出 state/node-2.copywrite.json + artifacts/copywrite/*

## 产出

- 状态文件：`state/node-2.copywrite.json`
- 产物：`artifacts/copywrite/script.md`（仿写全文）、`artifacts/copywrite/diff.md`（风格对比）

完成后 `handoff-ready` 通知可激活 node-3 / node-4 / node-5。

# 子命令：remotion — Remotion 合成专家

## 做什么

把数字人 + TTS 音频 + 字幕文案用 Remotion 合成为最终视频。核心职责不是"让视频能渲染出来"（那是 MVP 干的），而是"收敛 Remotion 代码的发散性"——产出**组件化、props 驱动、与文案同步**的可维护代码。

## 前置门禁（汇聚节点，三依赖必查）

```
state/node-2.copywrite.json     存在且 completed？  （字幕源）
state/node-3.tts.json           存在且 completed？  （音频+时长）
state/node-4.digital-human.json 存在且 completed？  （数字人视频）
  → 任一缺失：拒绝，提示缺哪个上游
  → 三者齐备：放行，进入合成流程
```

## 详细流程

**完整的 Remotion 代码结构规范、实现约束、质量门禁检查清单、产出 schema 见 [`references/expert-remotion.md`](./references/expert-remotion.md)。**

执行本子命令时，按该文档的流程跑：
1. 前置检查（三上游齐备）
2. 按 BLOCK 级目录结构规范产出代码（Root/Composition/components/props/utils 分层）
3. 强制四大约束（durationInFrames 对齐 TTS / 字幕走 props / 素材走 props / 类型集中定义）
4. 质量门禁（代码结构 + 数据驱动 + 时长校准 + 可构建，全过才 completed）
5. 产出 state/node-5.remotion.json + artifacts/remotion/src/

## 产出

- 状态文件：`state/node-5.remotion.json`
- 产物：`artifacts/remotion/src/`（完整可构建 Remotion 项目）、`artifacts/remotion/package.json`

完成后 `handoff-ready` 通知可激活 node-6。

## 内容团队 vs 开发专家的边界

| 决策类型 | 谁负责 |
|---------|--------|
| 创意层（字幕样式、转场效果、BGM 选择、视觉风格） | 内容团队 |
| 代码层（组件结构、props 设计、可构建性、可维护性） | 本专家（开发） |

内容团队可在 `props/default-props.ts` 调创意参数，不需要改组件代码——props 驱动设计让创意迭代不碰代码。

# 子命令：exit — 退出编排模式

清理运行时上下文，提示：

```
已退出专家编排模式。
  → state 和 artifacts 保留在 .gsd-expert/，随时可 /gsd-bianxiezhuanjia 再进入
  → 如需部署，/gsd-deploy
```

不删除任何文件。exit 只是"标记离开编排上下文"。

---

# 激活专家时的门禁（双重保险）

执行 `copywrite` / `remotion` 子命令时，本编排器先做一次前置检查（见各子命令的"前置门禁"），专家流程内部也会再查一次。门禁是 BLOCK 级：缺项必须拒绝，不能"先跑跑看"——发散节点上游错了，下游必然连锁出错。

---

# 编排器 vs 专家的边界

| 职责 | 谁做 |
|------|------|
| 扫描 state、显示进度、提示可激活 | 本编排器（status 子命令） |
| 激活前前置条件检查 | 本编排器 + 专家流程双重做 |
| 执行专家业务逻辑、收敛发散性 | 专家流程（copywrite / remotion 子命令） |
| 跑质量门禁检查清单 | 专家流程 |
| 写状态文件和产物 | 专家流程 |
| 决定"下一步调谁" | **人**（编排器只建议，不自动执行） |

**关键红线**：编排器**绝不自动执行**下游专家。人工接力模式下，每一步由人显式启动——这是框架"可审计、可把关"的根基。

# 与 gsd 工作流的衔接

| gsd 阶段 | 衔接 |
|---------|------|
| `/gsd-ship` 完成（MVP） | gsd 检测到 `.gsd-expert/` 或本框架配置 → 建议运行 `/gsd-bianxiezhuanjia` |
| `/gsd-bianxiezhuanjia` 运行中 | 编排模式，状态在 `.gsd-expert/` 流转 |
| 全部节点 completed | 本编排器提示「可用应用就绪，可 /gsd-deploy」 |
| `/gsd-deploy` | 消费 `.gsd-expert/artifacts/` 部署 |

本命令不改动 gsd 任何自带命令（`/gsd-plan` `/gsd-impl` `/gsd-ship` 原样），是 gsd 工作流里 MVP 之后、部署之前的一个**可选增强阶段**。
